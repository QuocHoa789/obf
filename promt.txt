2. ABSOLUTE RULE: PRESERVE EXISTING OBFUSCATION OUTPUT

This requirement takes priority over unnecessary refactoring, cosmetic improvements and optional features.

For the same input, seed, configuration, dependency versions and equivalent execution environment, preserve the exact output bytes produced by the original version whenever that behavior was already correct.

Preserve:

- Generated output source and formatting.
- Opcode mapping and instruction ordering.
- Constant pool contents and ordering.
- Serialization format and field ordering.
- Transformation pass ordering.
- Random-number generation and seed behavior.
- CLI arguments and existing API contracts.
- Output file paths and normal file-writing behavior.
- Existing deterministic behavior.
- Runtime semantics of successfully obfuscated programs.

Mandatory rules

- Never change the obfuscation algorithm simply to make the implementation cleaner.
- Never reorder transformations without evidence that the change is necessary.
- Never change random seeds or random-number generation to conceal a failure.
- Never add debug messages, timestamps, comments or instrumentation data to generated output.
- Never insert debugging code into the generated program.
- Never change successful outputs merely because the new output looks better.
- Never weaken existing tests to accommodate a regression.

A bug fix may change output for a previously failing input if necessary to correct the bug. However, the change must be documented, and previously successful inputs must remain protected by golden-output regression tests.

If a fix causes unexpected output differences, identify the responsible change and correct or revert it.

6. PHASE 4 — AUTOMATIC BUG DIAGNOSIS AND REPAIR

For every confirmed defect, follow this process:

1. Reproduce the failure.
2. Capture the diagnostic information.
3. Minimize the failing input where practical.
4. Identify the exact module and root cause.
5. Determine the smallest safe correction.
6. Implement the correction in the working copy.
7. Add a regression test that fails before the fix and passes afterward.
8. Run the affected test and related tests.
9. Run golden-output comparisons.
10. Run the broader test suite.
11. Document the result and any remaining uncertainty.

Prioritize defects in this order:

1. Crashes and incorrect program behavior.
2. Infinite loops, hangs and severe performance regressions.
3. Compiler, interpreter and VM correctness.
4. Serialization and deserialization corruption.
5. Runtime compatibility.
6. CLI and dependency failures.
7. Error messages, diagnostics and maintainability.

Fix root causes rather than suppressing symptoms.

Do not use empty "catch" blocks, fake success results, skipped assertions or weakened tests to make the suite appear healthy.

Do not modify unrelated code when the actual defect can be corrected locally.

If an error cannot be reproduced, document the evidence and investigate its possible triggers instead of inventing a fix.

If a repair cannot be completed safely, preserve the working implementation and report the unresolved issue.

Performance

- Per-test execution time.
- Slow compiler stages.
- Excessive memory consumption.
- Unexpected repeated transformations.

Test result classification

Every test must be classified accurately:

- "PASS": completed and met its assertions.
- "FAIL": completed but failed an assertion or encountered an error.
- "BLOCKED": could not run because of a missing dependency, runtime or environment limitation.
- "TIMEOUT": did not finish within its configured time limit.

Never count blocked or timed-out tests as passing.
